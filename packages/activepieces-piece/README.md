# Formfeed piece for Activepieces

`piece/` is the piece: `piece/src` is laid out like a folder under `packages/pieces/` of
[activepieces/activepieces](https://github.com/activepieces/activepieces), and `piece/README.md` is
its npm page. `build.mjs` turns it into the npm package `@formfeed/activepieces-piece`; everything else
here exists to check it in this repository.

## Why not a pull request

Since 2026-07-16 their repository closes pull requests from outside contributors automatically
(`CONTRIBUTING.md`, `close-external-prs.yml`); a piece of a vendor is expected to be published as
its own npm package. Talk to Activepieces before trying the community folder (the `keep-open` label).

Their framework is no longer released to npm either: npm has `@activepieces/pieces-framework`
0.32.0 from June 2026, while the repository is at 0.40, and their bundler inlines the framework into
the package. So the piece is **built in a checkout of their repository**, and this repository only
type-checks and tests it against 0.32.0, whose API the piece uses the same way
(`context.auth.secret_text`, `Property.*`, `createTrigger`). 0.32.0 does not yet export
`PieceCategory` from the framework; `support/framework.ts` supplies it here, so the source imports it
the way their repository wants.

## Checks

```sh
pnpm nx test activepieces-piece       # request shapes, every call against openapi.yaml, triggers
pnpm nx typecheck activepieces-piece
pnpm nx lint activepieces-piece
```

The two tests that read files outside the package (the logo, `openapi.json`) skip themselves in the
public repository, which exports only the packages.

## Release

The piece is one of the published packages: it is exported to the public repository
(`tools/public-repo`) and its `release.yml` publishes it on every `v*` tag, after the npm job has
checked the versions, with trusted publishing and provenance. Its version is the shared `VERSION` of
`tools/publish/packages.mjs`; there is nothing of its own to bump. 0.1.0 was published by hand on
2026-09-22 (npm lets a package trust a workflow only once it exists); from 0.3.8 on, the tag does it.

`build.mjs` does what their `publish-piece` would, without the parts that do not work for us:

1. Their repository at `ACTIVEPIECES_RELEASE` (a release tag, never `main`: on 2026-09-22 `main` did
   not compile under their own CLI, release `0.91.1` did), `bun install` with
   `REDISMS_DISABLE_POSTINSTALL=1` (a test helper otherwise builds Redis from source).
2. Their `createPiece('formfeed', '@formfeed/activepieces-piece', 'custom')`, called directly, because
   `npm run create-piece` only asks interactively.
3. `export.mjs` copies our sources and README into the checkout, then their translation file, turbo
   build and `preparePieceDistForPublish`, which inlines the framework and `form-data`.
4. README, LICENSE and the manifest fields their bundle leaves out (npm's provenance needs
   `repository` to be the public repository), into `dist/packages/activepieces-piece`.

Raise `ACTIVEPIECES_RELEASE` on purpose, after `node packages/activepieces-piece/build.mjs` passed
with the new tag. It needs Linux (their tooling does not run on Windows): in WSL, Node 24.14 through
nvm and `npm install -g bun@1.4.0`, the versions of their Dockerfile and `packageManager`, with the
checkout as its argument, e.g. `node packages/activepieces-piece/build.mjs ~/activepieces`. To try the
piece in Activepieces itself, `AP_DEV_PIECES=formfeed npm start` in the checkout (localhost:4200,
`dev@ap.com` / `12345678`; webhook triggers need a public tunnel).

A platform installs the piece by its npm name (**Platform Admin → Setup → Pieces → Install Piece**);
on Activepieces Cloud that may need a paid plan, which is not verified.

The logo is `https://formfeed.dev/brand/formfeed-512.png`, generated by `pnpm nx run brand:icons`.
